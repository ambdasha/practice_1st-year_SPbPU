# Прогноз риска задержки доставки заказов

Проект по прогнозированию задержки доставки заказов интернет-магазина на основе данных **Olist Brazilian E-Commerce**.

Задача модели — в момент подтверждения заказа оценить вероятность того, что заказ будет доставлен позже обещанного срока. Такой прогноз можно использовать для раннего выявления проблемных заказов и их приоритизации для дополнительного контроля.

## Постановка задачи

В качестве ML-задачи рассматривается бинарная классификация:

> определить, будет ли заказ доставлен позже срока, который был обещан покупателю.

Прогноз строится на момент:

```text
order_approved_at
```

То есть модель может использовать только ту информацию, которая уже известна на момент подтверждения заказа.

Это важно, поскольку часть признаков в исходном датасете появляется уже после отправки или доставки заказа и при использовании в модели приводит к утечке целевой переменной.

В практическом сценарии результат модели можно использовать не только как бинарный прогноз, но и как **оценку риска** для ранжирования заказов.

Например, если операционная команда способна дополнительно проверить только 10% заказов, в работу можно отправлять заказы с наибольшей предсказанной вероятностью задержки.

## Данные

Используется открытый датасет **Olist Brazilian E-Commerce Dataset**.

Исходные данные представлены несколькими связанными таблицами:

* заказы;
* товары в заказах;
* покупатели;
* продавцы;
* товары;
* платежи;
* отзывы;
* географические данные.

После объединения и фильтрации итоговая выборка содержит:

```text
96 456 заказов
```

Гранулярность итогового датасета:

```text
1 строка = 1 заказ
```

Это потребовало предварительной агрегации таблиц, где одному заказу соответствует несколько строк, например `order_items` и `order_payments`.

## Целевая переменная

Целевая переменная:

```text
late_delivery
```

Определяется следующим образом:

```text
late_delivery = 1,
если фактическая дата доставки позже обещанной даты

late_delivery = 0,
если заказ доставлен вовремя
```

Распределение классов:

| Класс                 | Количество |   Доля |
| --------------------- | ---------: | -----: |
| Доставлен вовремя     |     89 922 | 93.23% |
| Доставлен с задержкой |      6 534 |  6.77% |

Задача имеет заметный дисбаланс классов, поэтому `accuracy` практически не используется для оценки моделей.

## Особенности задачи

### Дисбаланс классов

Только около 6.8% заказов относятся к положительному классу.

При таком распределении модель, всегда предсказывающая отсутствие задержки, получила бы accuracy выше 93%, но не имела бы никакой практической ценности.

Поэтому основной акцент сделан на:

* PR-AUC;
* ROC-AUC;
* Precision;
* Recall;
* F1;
* Top-K Lift.

### Временная зависимость

Данные имеют выраженную временную структуру.

Доля задержанных заказов и характеристики заказов меняются со временем, поэтому случайное разделение `train_test_split` может давать слишком оптимистичную оценку качества.

В проекте используется временное разделение данных.

### Data Leakage

Особое внимание уделено историческим признакам продавцов.

Например, средняя доля задержек конкретного продавца может быть сильным признаком. Но при ее неправильном расчете в признаки текущего заказа могут попасть результаты будущих доставок.

Поэтому история продавца рассчитывается только по тем заказам, результат доставки которых уже был известен на момент формирования текущего прогноза.

### Характеристики товаров

Характеристики товаров агрегируются до уровня заказа.

Используются:

* количество категорий;
* вес товаров;

### Географические признаки

На основе таблицы геолокации определяются приблизительные координаты покупателя и продавцов.

Расстояние рассчитывается по формуле Haversine.

Используются:

* среднее расстояние между продавцом и покупателем;
* минимальное расстояние;
* максимальное расстояние;
* разброс расстояний;
* доля продавцов из того же штата;
* наличие пропущенных географических данных.

Географические признаки оказались полезны, поскольку расстояние напрямую связано со сложностью логистики и временем доставки.

---

### Платежные признаки

Платежи также агрегируются до уровня заказа.

Используются:

* количество платежных операций;
* количество способов оплаты;
* итоговая сумма платежа;
* максимальное количество платежных периодов;
* использование кредитной карты;
* использование boleto;
* использование voucher;
* использование debit card.

---

### История продавца

Для каждого продавца рассчитываются признаки на основе уже завершенных заказов:

* количество предыдущих доставленных заказов;
* историческая доля задержек;
* средняя задержка;
* максимальная задержка;
* количество дней с последней известной доставки;
* наличие достаточной истории продавца.

Эти признаки позволяют учитывать надежность конкретного продавца.

## Защита от Data Leakage

История продавца строится с учетом момента, когда результат предыдущего заказа действительно стал известен.

Для текущего заказа с временем прогноза `t` предыдущий заказ разрешено использовать только если:

```text
previous_order.order_delivered_customer_date
<
current_order.order_approved_at
```

Недостаточно просто проверить, что предыдущий заказ был создан раньше.

Например, заказ мог быть оформлен неделю назад, но все еще находиться в доставке. На момент построения текущего прогноза неизвестно, будет он доставлен вовремя или нет.

Использование такого результата привело бы к утечке информации из будущего.

## Разделение выборки

Вместо случайного разбиения используется **temporal split**.

| Выборка    | Количество | Доля задержек |
| ---------- | ---------: | ------------: |
| Train      |     67 519 |         7.83% |
| Validation |     14 468 |         4.34% |
| Test       |     14 469 |         4.28% |

Периоды:

```text
Train
2016-09-15 → 2018-04-16

Validation
2018-04-16 → 2018-06-21

Test
2018-06-21 → 2018-08-29
```

Логика такого разделения:

```text
прошлое → train

более новые данные → validation

будущее → test
```

Таким образом, итоговая оценка лучше соответствует реальному сценарию эксплуатации модели.

Также заметно изменение доли положительного класса:

```text
Train:      7.83%
Validation: 4.34%
Test:       4.28%
```

Это указывает на наличие временного drift в данных.

## Модели

В проекте сравниваются несколько подходов.

### DummyClassifier

Используется как базовая точка отсчета.

Модель необходима для проверки того, что обучаемые алгоритмы действительно извлекают полезный сигнал из данных.

### Logistic Regression

Линейная baseline-модель.

Для числовых признаков используются:

* заполнение пропусков медианой;
* масштабирование.

Для категориальных:

* заполнение наиболее частым значением;
* One-Hot Encoding.

Для компенсации дисбаланса используется взвешивание классов.

### Random Forest

Используется как нелинейная ансамблевая модель.

Настройки ограничивают сложность деревьев и учитывают дисбаланс классов.

### CatBoost

Основная градиентная модель проекта.

CatBoost позволяет работать с категориальными признаками без предварительного One-Hot Encoding и хорошо подходит для табличных данных.

Дополнительно CatBoost использовался для:

* Feature Importance;
* SHAP-анализа;
* анализа отдельных предсказаний;
* Top-K анализа.

## Метрики

В качестве основных метрик используются:

### ROC-AUC

Показывает способность модели правильно ранжировать положительные и отрицательные объекты.

### PR-AUC

Для данной задачи является одной из основных метрик из-за сильного дисбаланса классов.

Она лучше отражает качество модели именно на положительном классе.

### Precision

```text
Precision = TP / (TP + FP)
```

Показывает, какая доля заказов, помеченных моделью как рискованные, действительно была доставлена с задержкой.

### Recall

```text
Recall = TP / (TP + FN)
```

Показывает, какую долю всех задержанных заказов удалось найти.

### F1

Баланс между Precision и Recall.

### Top-K Lift

Используется для оценки качества ранжирования заказов по риску.

## Top-K анализ

Для бизнеса необязательно переводить вероятность модели в жесткий класс `0/1`.

Другой вариант — отсортировать заказы по вероятности задержки и работать только с наиболее рискованными.

Для CatBoost на validation:

| Доля заказов | Late Rate |  Lift | Найдено всех задержек |
| -----------: | --------: | ----: | --------------------: |
|       Top 1% |    18.62% | 4.29x |                 4.30% |
|       Top 5% |    15.61% | 3.60x |                17.99% |
|      Top 10% |    13.48% | 3.10x |                31.05% |
|      Top 20% |    10.26% | 2.36x |                47.29% |
|      Top 30% |     8.52% | 1.96x |                58.92% |

Средняя доля задержек на validation:

```text
4.34%
```

При этом среди **Top 10% наиболее рискованных заказов** задерживается:

```text
13.48%
```

То есть концентрация проблемных заказов примерно в:

```text
3.1 раза
```

выше среднего.

При проверке только 10% заказов можно найти около:

```text
31% всех задержанных заказов
```

Это делает модель полезной прежде всего как систему ранжирования риска.

## Анализ ошибок

Отдельно анализируются:

```text
False Positive
```

заказы, которые модель посчитала рискованными, но которые были доставлены вовремя.

И:

```text
False Negative
```

заказы, которые модель посчитала безопасными, но которые в итоге задержались.

Проводится анализ ошибок по:

* штатам;
* категориям товаров;
* месяцам;
* уровню предсказанного риска.

Также построены:

* confusion matrix;
* распределение вероятностей;
* calibration curve.

Для отдельных объектов рассматриваются локальные SHAP-объяснения.

## Основные выводы

В ходе работы над проектом получилось несколько важных результатов.

**1. Temporal split существенно влияет на оценку качества.**

Результаты на будущем периоде заметно хуже validation, что не было бы так очевидно при случайном разделении данных.

**2. Более сложная модель не всегда показывает лучший результат.**

На итоговом test лучшей моделью оказалась Logistic Regression, несмотря на использование Random Forest и CatBoost.

**3. Исторические признаки продавца полезны, но требуют аккуратной реализации.**

При их построении необходимо учитывать не дату создания предыдущего заказа, а момент, когда результат его доставки уже был известен.

**4. Для несбалансированной задачи недостаточно Accuracy.**

В проекте основной упор сделан на PR-AUC, Recall, Precision и Top-K Lift.

**5. Модель можно использовать как ranking-систему.**

Даже при сравнительно небольшой абсолютной Precision верхняя часть распределения риска содержит значительно большую концентрацию задержанных заказов.

**6. В данных присутствует временной drift.**

Для production-системы потребуется мониторинг распределений и регулярное переобучение.

## Что можно улучшить

Следующие шаги развития проекта:

* rolling / expanding temporal cross-validation;
* подбор гиперпараметров моделей;
* более подробный анализ temporal drift;
* оптимизация threshold через стоимость ошибок;
* probability calibration;
* перенос полного Feature Engineering из notebook в `src`;
* полноценный inference pipeline;
* подключение модели к FastAPI;
* расширение unit и integration tests;
* полноценное логирование экспериментов через MLflow;
* мониторинг качества модели после развертывания.
